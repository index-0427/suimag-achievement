# 実績追加ガイド

実績の定義は [`achievements/`](../achievements/) の作者別ファイルにまとめます。標準実績は [`00_default.lua`](../achievements/00_default.lua) にあります。サーバー・クライアント・UIの本体を変更せず、定義と必要な判定処理だけを用意できます。新しい依存パッケージやSQLは不要です。

## 1. 判定方法を選ぶ

| 達成条件 | 定義の `auto` | 追加で必要な処理 |
| --- | --- | --- |
| 定義追加後の初ログイン | `'join'` | なし。ログイン時に即時達成 |
| 累計接続時間 | `'playtime'` | なし。`target` は分単位 |
| 配達・採集・イベント参加など | 項目自体を省略 | 外部リソースのサーバーで条件を確認し、exportsを呼ぶ |

`auto` にジョブ名やイベント名を書いても連携されません。自動判定は上の2種類だけです。

## 2. 作者別ファイルを追加する

`achievements/10_author_a.lua` のように、作者名を含むファイルを作ります。次の内容は**ファイル全体**としてコピーできます。実際の作者名に合わせてファイル名を変更してください。

```lua
-- 作者: author_a / 配達に関する実績
return {
    {
        id = 'delivery_10',
        name = '配達の達人',
        description = '配達を10回完了する。',
        title = '配達人',
        target = 10,
        unit = '回',
    },
}
```

同じ作者の実績を増やすときは、この `return { ... }` の内側へ `{ ... },` を追加します。別の作者は別ファイルを追加すればよく、他人のファイルや読み込み対象一覧を編集する必要はありません。

この例は外部連携用なので、定義だけでは進捗は増えません。次の節のサーバー処理も必要です。

### 読み込みと表示順

- 対象は `achievements/` **直下**の、拡張子が小文字 `.lua` のファイルです。サブフォルダは対象外です。
- 表示順はファイル名の昇順、そのファイル内の記載順です。半角小文字の名前と `00_` / `10_` / `20_` のような数字の接頭辞を使うと順番を管理しやすくなります。
- ファイル追加・編集・削除はリソース再起動時に反映されます。`fxmanifest.lua` への追記は不要です。
- 各ファイルは定義の配列を `return` します。`Config.Achievements = ...` と書いたり、別ファイルの変数を参照したりしません。条件判定やイベント登録は外部ジョブのサーバー処理で行います。
- 全ファイルを通して `id` は一意にします。別の人と重なる場合は `author_a_delivery_10` のような接頭辞を付け、そのIDをジョブ側でも使用します。
- 一時的に外す場合はフォルダの外へ移すか、拡張子を `.lua.disabled` などに変更します。`return {}` の空ファイルも使えます。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| `id` | はい | 重複しない半角英数字・`_`・`-`。保存キーとAPI呼び出しに使用 |
| `name` | はい | 一覧に表示する実績名。空文字不可 |
| `description` | はい | 達成条件の説明（文字列） |
| `title` | はい | 達成後に選択できる称号。空文字・改行・`~` は不可 |
| `target` | はい | 目標値。1以上の整数 |
| `unit` | いいえ | 進捗の単位。文字列。省略時は「回」 |
| `auto` | いいえ | `'join'` / `'playtime'`。外部連携の場合は省略 |

名前と称号は同じでなくても構いません。日本語の値も使用できます。定義の末尾には `},` を付けます。以下の例は、作者別ファイルの `return { ... }` の内側に追加する定義ブロックです。

### 定義だけで動く例

ログイン実績（`target = 1`）:

```lua
    {
        id = 'festival_visit',
        name = 'お祭りへようこそ',
        description = 'この実績の追加後にログインする。',
        title = 'お祭り参加者',
        target = 1,
        auto = 'join',
    },
```

これは会場への到着判定ではありません。定義追加後にログインしたキャラクター全員が対象で、リソース再起動時に接続済みのキャラクターも含みます。

接続時間の実績（30分）:

```lua
    {
        id = 'thirty_minutes',
        name = '街を散策',
        description = 'この街で合計30分を過ごす。',
        title = '散策中',
        target = 30,
        auto = 'playtime',
        unit = '分',
    },
```

接続時間はキャラクター別の累計です。離席も含み、オフライン・キャラクター選択中は含みません。本リソース導入前の時間は遡れません。後から時間実績を追加した場合、本リソースが既に保存した累計時間は次回の接続時間更新（約1分ごと）で反映されます。

## 3. 外部ジョブから加算する

連携するジョブ側の `fxmanifest.lua` に次を追加し、実績リソースが先に起動するようにします。

```lua
dependency 'suimag-achievement'
```

ジョブ側の**サーバースクリプト**で、既に配達完了を検証している処理の成功箇所へ挿入します。`playerId` はその処理で確定したプレイヤーのサーバーIDです。

```lua
local ok, reason = exports['suimag-achievement']:AddProgress(playerId, 'delivery_10', 1)
if not ok then
    print(('[delivery] 実績の加算に失敗: %s'):format(reason))
end
```

1回のイベント参加など、カウントせず即時達成させる場合は、同じ成功箇所で `AddProgress` の代わりに次を使います。

```lua
local ok, reason = exports['suimag-achievement']:Unlock(playerId, 'delivery_10')
if not ok then
    print(('[delivery] 実績の達成に失敗: %s'):format(reason))
end
```

- クライアントが送った「完了した」「10回分」などの申告を、そのまま加算しないでください。対象プレイヤー・進行中のジョブ・完了条件を既存のサーバー処理で検証します。
- 報酬処理などと同じ、一度だけ成功が確定する箇所で呼びます。同じ完了を2回通知すると2回加算されます。`AddProgress` と `Unlock` の両方を呼ぶ必要はありません。
- イベント内で `source` を使う場合、`Wait` やDB待機より前に `local playerId = source` として保持します。クライアント指定の他人のIDを採用しないでください。
- 対象はオンライン中のキャラクターです。失敗してもジョブ報酬を再配布したり、未検証の値で再試行したりしないでください。

### APIと戻り値

| 呼び出し | 動作 |
| --- | --- |
| `AddProgress(playerId, id, amount)` | 正の整数を加算。`amount` 省略時は1、上限は2147483647 |
| `Unlock(playerId, id)` | その実績を即時達成 |

成功時は `true`、失敗時は `false, reason` を返します。進捗は目標値で止まり、達成済みに再度呼んでも達成日は変わりません。画面への更新通知・保存・称号の選択可否は本体が処理します。

| `reason` | 確認箇所 |
| --- | --- |
| `unknown_achievement` | 定義と呼び出しのIDが同じか。定義追加後に再起動したか |
| `invalid_amount` | 加算値が正の整数か。文字列・小数・上限超過でないか |
| `player_unavailable` | 対象キャラクターがログイン中か。サーバーログに保存データの破損エラーがないか |

リソース停止中のexports呼び出しはこの戻り値とは別のエラーになります。連携ジョブと実績リソースを稼働させた状態で確認してください。

## 4. 確認して渡す

1. 作者別ファイルを保存し、開発環境で `node tests/run.js` を実行します。追加ファイルを含む全Lua定義を読み込みます。標準3実績を残した構成で回帰テストできます。
2. 運用担当者がテストサーバーへ変更を配置し、`suimag-achievement` を再起動します。外部ジョブを変更した場合はその変更も反映します。サーバー操作に承認が必要な環境では、その手順に従ってください。
3. スマホの「実績」で名前・説明・目標・表示順を確認します。
4. 実際の条件を1回満たし、意図した分だけ増えること、未達成時は称号を選べないこと、達成後は選択・解除できることを確認します。
5. 再ログイン後の進捗・選択称号と、別キャラクターに引き継がれないことを確認します。取得率は次の定期集計まで反映されません（標準2時間）。

定義エラーは、例えば `achievements/10_author_a.lua #1 (delivery_10): target must be a positive integer` のように、ファイル名・ファイル内の順番・ID・問題の項目をサーバーログへ表示し、実績処理の初期化を中止します。重複IDの場合は、先に定義されたファイル名と位置も表示します。構文エラーの場合はLuaがファイル名と行番号を表示します。

第三者から渡すものは、**作者別の `.lua` ファイル、外部ジョブ側の変更（必要な場合）、実際の達成条件と確認結果**です。ログイン・時間実績なら作者別ファイルだけで構いません。画面用ファイルや保存処理を複製する必要はありません。

## 公開済みの実績を変更するとき

- `id` / `target` は原則固定です。条件を変える場合は新しいIDで追加します。IDを再利用すると、過去の進捗が別の実績へ引き継がれます。
- 名前・説明・称号・表示順は編集できます。変更後は再起動してください。称号名の変更はその称号を選択中のキャラクターにも反映されます。
- 定義を削除してもKVPの記録は残りますが、一覧や称号には使われません。同じIDを再追加すると過去の記録が再び使われます。
- ファイル名は保存キーではありません。作者別ファイルの改名や実績のファイル間移動では、`id` を維持すれば進捗・称号は引き継がれます。
- 旧版の `config.lua` または単一の `achievements.lua` に独自定義がある場合は、更新前に退避し、作者別ファイルへ同じID・目標値で移します。外側の `Config.Achievements = { ... }` は `return { ... }` に変更します。旧ファイルは読み込まれないため、移行漏れがないか確認してください。DBやKVPの移行は不要です。
